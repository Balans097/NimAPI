# system/alloc.nim — справочник модуля (публичный API)

> **Импорт:** отдельного `import` не требуется. `alloc.nim` подключается в `system.nim`
> директивой `include`, поэтому его процедуры становятся частью модуля `system`
> и доступны в любой Nim-программе без явного импорта.
> **Область применения:** низкоуровневый аллокатор кучи, обслуживающий как
> ручное управление памятью (`alloc`/`dealloc`), так и сборщик мусора.

Этот файл реализует аллокатор памяти уровня рантайма Nim: TLSF-подобную схему
для "больших" блоков и схему ячеек с общим "аккумулятором" для "маленьких"
блоков внутри разделяемых на страницы чанков. Ниже описан только
**публично используемый слой** — процедуры, которые вызывает обычный
Nim-код (`alloc`, `dealloc`, `realloc`, `allocShared`, `getFreeMem` и т.п.).
Внутренняя механика (TLSF-матрица `flBitmap`/`slBitmap`, AVL-дерево для
интервального поиска, `IntSet` для множества стартов чанков, сама структура
`MemRegion`) устройство памяти вообще не документируется процедура-за-процедурой —
ей посвящён только сводный обзор в разделе VI.

Общая конвенция модуля: у каждой операции есть пара "потоковая /
разделяемая" (`alloc` работает с кучей текущего потока, `allocShared` — с
кучей, доступной из любого потока), а суффикс `0` означает "с обнулением
памяти" (`alloc0`, `realloc0`, `allocShared0`).

## I. Модель памяти и тип `MemRegion`

### 1. `MemRegion`

```nim
type MemRegion = object
```

**Что делает.** `MemRegion` — это одна "куча": самодостаточная структура
данных со своими чанками, битовыми картами TLSF, AVL-деревом больших
блоков и списками свободных маленьких ячеек. В обычной программе одна
`MemRegion` создаётся неявно на поток (потоковая куча) и ещё одна —
как общая (shared) куча для `allocShared`. Тип не экспортируется и
напрямую пользовательским кодом не создаётся: вся работа с ним идёт
через процедуры разделов II–V, которые уже привязаны к нужному экземпляру.

- **Параметры**: нет (тип используется только как неявный получатель
  во внутренних процедурах; наружу он не выходит).

---

### 2. Устройство "чанков" (кратко)

Память региона делится на **чанки**, каждый из которых начинается по
адресу, кратному размеру страницы:

- **Маленький чанк** (`SmallChunk`, размер — одна страница) режется на
  ячейки одного класса размера; ячейки переиспользуются через связный
  список свободных ячеек и общий "аккумулятор" (сдвигающийся указатель
  на ещё не тронутую часть чанка).
- **Большой чанк** (`BigChunk`) выделяется под запросы, которые не
  помещаются в маленький чанк; такие чанки хранятся в TLSF-матрице
  по классам размера и могут сливаться (coalescing) с соседями при
  освобождении.
- **Огромный чанк** (превышающий `HugeChunkSize`) выделяется и
  освобождается напрямую через операционную систему, минуя матрицу.

Публичные процедуры ниже сами решают, какой из трёх путей использовать,
исходя из размера запроса — вызывающему коду об этом заботиться не нужно.

## II. Выделение и освобождение памяти текущего потока

### 1. `alloc`

```nim
proc alloc(size: Natural): pointer {.gcsafe.}
```

**Что делает.** Выделяет `size` байт нетипизированной памяти в куче
текущего потока и возвращает указатель на неё. Содержимое памяти **не**
гарантированно обнулено — используйте `alloc0`, если это важно. Если
`size` равен 0, поведение определяется внутренним округлением размера
(будет выделен минимальный возможный блок, а не `nil`).

- **Разбор реализации.** Для запросов, помещающихся в маленький чанк,
  память берётся почти бесплатно: либо сдвигается "аккумулятор" чанка,
  либо снимается голова списка свободных ячеек — обе операции O(1).
  Для более крупных запросов используется поиск подходящего блока в
  TLSF-матрице (тоже амортизированно O(1) благодаря битовым картам),
  и при необходимости — запрос новых страниц у ОС.

- **Параметры**:
  - `size: Natural` — требуемый размер в байтах (неизменяемый вход).

- **Примеры**:

```nim
# Типичный случай: выделяем память под объект и работаем через приведение типов.
type
  Vec3 = object
    x, y, z: float32

var p = cast[ptr Vec3](alloc(sizeof(Vec3)))
p.x = 1.0
p.y = 2.0
p.z = 3.0
echo p.x, " ", p.y, " ", p.z  # выводит 1.0 2.0 3.0
dealloc(p)                    # каждому alloc должен соответствовать dealloc

# Граничный случай: нулевой размер — исключения не будет,
# но возвращённым указателем нельзя пользоваться для хранения данных.
var empty = alloc(0)
dealloc(empty)
```

---

### 2. `alloc0`

```nim
proc alloc0(size: Natural): pointer
```

**Что делает.** То же самое, что `alloc`, но дополнительно обнуляет все
`size` байт перед возвратом указателя. Полезно там, где важна
предсказуемость начального состояния памяти (например, буферы, которые
затем интерпретируются как массив чисел).

- **Разбор реализации.** Реализация — это тонкая обёртка: сначала
  вызывается `alloc`, затем `zeroMem` проходит по всему диапазону.
  Дополнительная стоимость линейна по размеру и заметна только на
  больших буферах.

- **Параметры**:
  - `size: Natural` — требуемый размер в байтах.

- **Примеры**:

```nim
# Типичный случай: массив int, гарантированно нулевой.
var arr = cast[ptr UncheckedArray[int]](alloc0(5 * sizeof(int)))
echo arr[0], " ", arr[4]  # выводит 0 0
dealloc(arr)

# Практический сценарий: буфер-счётчик, куда далее только прибавляют значения.
var counters = cast[ptr UncheckedArray[int32]](alloc0(256 * sizeof(int32)))
inc(counters[10])
inc(counters[10])
echo counters[10]  # выводит 2 — стартовое значение гарантированно было 0
dealloc(counters)
```

---

### 3. `dealloc`

```nim
proc dealloc(p: pointer)
```

**Что делает.** Освобождает память, ранее полученную через `alloc` или
`alloc0` **в той же куче потока**. После вызова указатель `p`
использовать нельзя — доступ к уже освобождённой памяти является
неопределённым поведением, а не поднимает исключение Nim. Повторный
`dealloc` того же указателя (двойное освобождение) — тоже неопределённое
поведение и не может быть безопасно продемонстрировано через
`doAssertRaises`.

- **Разбор реализации.** В зависимости от того, к маленькому или
  большому чанку принадлежит указатель, ячейка либо возвращается в
  список свободных ячеек чанка (и при исчерпании чанка не освобождается
  на месте — есть отдельная защита от гонки между потоками при работе с
  общими списками ячеек), либо чанк передаётся в TLSF-матрицу и может
  слиться с соседними свободными чанками.

- **Параметры**:
  - `p: pointer` — указатель, ранее возвращённый `alloc`/`alloc0`
    (изменяется логически — становится недействительным).

- **Примеры**:

```nim
# Типичный случай.
var p = alloc(64)
dealloc(p)

# Практический сценарий: освобождение в конце области видимости через defer.
proc useTemporaryBuffer() =
  var buf = alloc(1024)
  defer: dealloc(buf)
  # ... работа с buf ...
  discard
useTemporaryBuffer()
```

---

### 4. `realloc`

```nim
proc realloc(p: pointer, newSize: Natural): pointer
```

**Что делает.** Изменяет размер ранее выделенного блока на `newSize`
байт, сохраняя содержимое в пределах `min(старый_размер, newSize)` байт,
и возвращает указатель на (возможно новый) блок. Если `p` равен `nil`,
ведёт себя как `alloc(newSize)`. Если `newSize` равен 0, блок
освобождается и возвращается `nil`.

- **Разбор реализации.** В отличие от классического `realloc` из C,
  здесь нет попытки "расширить блок на месте": реализация всегда
  выделяет новый блок нужного размера, копирует данные через `copyMem`
  и освобождает старый. Это проще и safer относительно фрагментации
  ценой лишнего копирования при частом росте — отсюда практическая
  рекомендация роста буфера с запасом (см. раздел VII, рецепт 2).

- **Параметры**:
  - `p: pointer` — указатель на существующий блок либо `nil`.
  - `newSize: Natural` — новый требуемый размер в байтах.

- **Примеры**:

```nim
# Типичный случай: рост буфера.
var buf = cast[ptr UncheckedArray[int32]](alloc(4 * sizeof(int32)))
buf[0] = 1
buf[1] = 2
buf[2] = 3
buf[3] = 4
buf = cast[ptr UncheckedArray[int32]](realloc(buf, 8 * sizeof(int32)))
echo buf[0], " ", buf[3]  # выводит 1 4 — старые данные сохранены
dealloc(buf)

# Граничный случай: newSize == 0 эквивалентно dealloc.
var p = alloc(16)
p = realloc(p, 0)
echo p == nil  # выводит true
```

---

### 5. `realloc0`

```nim
proc realloc0(p: pointer, oldSize, newSize: Natural): pointer
```

**Что делает.** То же самое, что `realloc`, но дополнительно обнуляет
"хвост" — байты между `oldSize` и `newSize`, если новый размер больше
старого. В отличие от `realloc`, требует явно передать старый размер
`oldSize`, так как именно от него отсчитывается граница обнуления.

- **Разбор реализации.** Обёртка над `realloc`: после копирования старых
  данных `zeroMem` обнуляет только "новую" часть буфера
  (`newSize - oldSize` байт), не трогая уже скопированные данные.

- **Параметры**:
  - `p: pointer` — указатель на существующий блок либо `nil`.
  - `oldSize: Natural` — прежний размер блока в байтах (нужен только
    для вычисления границы обнуления).
  - `newSize: Natural` — новый требуемый размер в байтах.

- **Примеры**:

```nim
# Типичный случай: расширение буфера с гарантией нулей в новом хвосте.
var buf = cast[ptr UncheckedArray[byte]](alloc0(4))
buf[0] = 1
buf = cast[ptr UncheckedArray[byte]](realloc0(buf, 4, 8))
echo buf[0], " ", buf[4], " ", buf[7]  # выводит 1 0 0
dealloc(buf)
```

## III. Разделяемая (shared) память между потоками

### 1. `allocShared`

```nim
proc allocShared(size: Natural): pointer {.gcsafe.}
```

**Что делает.** Выделяет `size` байт в куче, общей для всех потоков
программы. Память, полученную отсюда, можно передать в другой поток и
безопасно освободить там же через `deallocShared` — в отличие от
памяти, полученной через `alloc`, которая привязана к потоку-владельцу.

- **Разбор реализации.** При наличии поддержки потоков доступ к общей
  куче защищён блокировкой (`heapLock`); без поддержки потоков это
  просто псевдоним обычного `alloc`. Для случая с деструкторами GC
  вместо блокировки используются lock-free списки отложенного
  освобождения — освобождение "чужой" памяти не блокирует поток, а
  откладывает фактическое высвобождение до следующего обращения
  владельца (подробнее — раздел VI).

- **Параметры**:
  - `size: Natural` — требуемый размер в байтах.

- **Примеры**:

```nim
# Типичный случай: буфер, который будет освобождён из другого потока.
var shared = allocShared(128)
deallocShared(shared)
```

---

### 2. `allocShared0`

```nim
proc allocShared0(size: Natural): pointer
```

**Что делает.** Обнуляющий вариант `allocShared` — аналогично паре
`alloc`/`alloc0`.

- **Параметры**:
  - `size: Natural` — требуемый размер в байтах.

- **Примеры**:

```nim
var shared = cast[ptr UncheckedArray[int]](allocShared0(4 * sizeof(int)))
echo shared[0]  # выводит 0
deallocShared(shared)
```

---

### 3. `deallocShared`

```nim
proc deallocShared(p: pointer)
```

**Что делает.** Освобождает блок, выделенный через `allocShared`/
`allocShared0`. В отличие от обычного `dealloc`, безопасно вызывать из
потока, отличного от того, что выделял память — именно в этом
практическая ценность разделяемой кучи.

- **Разбор реализации.** Если освобождающий поток совпадает с
  владельцем чанка, освобождение происходит немедленно; иначе блок
  кладётся в список отложенного освобождения владельца и фактически
  высвобождается позже, за счёт этого не требуется держать блокировку
  на время самой операции освобождения.

- **Параметры**:
  - `p: pointer` — указатель, ранее возвращённый `allocShared`/
    `allocShared0`.

- **Примеры**:

```nim
var shared = allocShared(64)
deallocShared(shared)
```

---

### 4. `reallocShared` / `reallocShared0`

```nim
proc reallocShared(p: pointer, newSize: Natural): pointer
proc reallocShared0(p: pointer, oldSize, newSize: Natural): pointer
```

**Что делает.** Полные аналоги `realloc`/`realloc0`, но для разделяемой
кучи: изменяют размер блока, сохраняя данные, `reallocShared0`
дополнительно обнуляет новый хвост.

- **Параметры**: те же, что у `realloc`/`realloc0` (см. выше), но
  указатель должен быть получен из `allocShared`/`allocShared0`.

- **Примеры**:

```nim
var shared = cast[ptr UncheckedArray[int32]](allocShared(4 * sizeof(int32)))
shared[0] = 42
shared = cast[ptr UncheckedArray[int32]](reallocShared(shared, 8 * sizeof(int32)))
echo shared[0]  # выводит 42
deallocShared(shared)
```

## IV. Статистика и диагностика памяти

### 1. `getFreeMem`

```nim
proc getFreeMem(): int
```

**Что делает.** Возвращает количество байт, которые куча текущего
потока уже запросила у операционной системы, но в данный момент не
использует под живые объекты (то есть доступно для будущих `alloc` без
обращения к ОС).

- **Параметры**: нет.

- **Примеры**:

```nim
let before = getFreeMem()
var p = alloc(1024)
let after = getFreeMem()
echo before >= after  # выводит true — свободной памяти стало не больше
dealloc(p)
```

---

### 2. `getTotalMem`

```nim
proc getTotalMem(): int
```

**Что делает.** Возвращает суммарный объём памяти (в байтах), который
куча текущего потока когда-либо запросила у операционной системы и
всё ещё удерживает (занятая часть плюс свободная часть внутри уже
полученных страниц).

- **Параметры**: нет.

- **Примеры**:

```nim
echo getTotalMem() >= getFreeMem()  # выводит true — общий объём не меньше свободного
```

---

### 3. `getOccupiedMem`

```nim
proc getOccupiedMem(): int
```

**Что делает.** Возвращает объём памяти (в байтах), реально занятой
живыми объектами прямо сейчас, то есть `getTotalMem() - getFreeMem()`
по сути (хотя внутри ведётся отдельным счётчиком, а не вычисляется
каждый раз вычитанием).

- **Параметры**: нет.

- **Примеры**:

```nim
let before = getOccupiedMem()
var p = alloc(256)
echo getOccupiedMem() > before  # выводит true
dealloc(p)
```

---

### 4. `getMaxMem`

```nim
proc getMaxMem*(): int
```

**Что делает.** Возвращает исторический максимум объёма памяти,
удерживаемой кучей за всё время работы программы — то есть пиковое
значение `getTotalMem()`, а не текущее.

- **Разбор реализации.** Пиковое значение обновляется не при каждом
  выделении, а лишь в момент освобождения страниц назад операционной
  системе (`decCurrMem`), поэтому фактически возвращается
  `max(текущее_значение, последний_зафиксированный_пик)` — это и
  учитывает случай, когда текущий момент сам является новым пиком.

- **Параметры**: нет.

- **Примеры**:

```nim
var p = alloc(1024 * 1024)
let peak = getMaxMem()
dealloc(p)
echo getMaxMem() >= peak  # выводит true — пик не уменьшается после освобождения
```

---

### 5. `getFreeSharedMem` / `getTotalSharedMem` / `getOccupiedSharedMem`

```nim
proc getFreeSharedMem(): int
proc getTotalSharedMem(): int
proc getOccupiedSharedMem(): int
```

**Что делает.** Полные аналоги трёх процедур статистики выше
(`getFreeMem`, `getTotalMem`, `getOccupiedMem`), но для разделяемой
(shared) кучи, а не для кучи текущего потока.

- **Разбор реализации.** При отсутствии поддержки деструкторов GC
  доступ к счётчикам разделяемой кучи защищён той же блокировкой, что
  и сами операции `allocShared`/`deallocShared`.

- **Параметры**: нет.

- **Примеры**:

```nim
var shared = allocShared(4096)
echo getOccupiedSharedMem() > 0  # выводит true
deallocShared(shared)
```

---

### 6. `getMemCounters`

```nim
proc getMemCounters*(): (int, int)
```

**Что делает.** Возвращает пару счётчиков `(количество вызовов alloc,
количество вызовов dealloc)` для кучи текущего потока. Доступна только
при компиляции с `-d:nimTypeNames` — в остальных сборках процедура не
существует вовсе.

- **Параметры**: нет.

- **Примеры**:

```nim
# Компилировать с -d:nimTypeNames, иначе процедура недоступна.
when defined(nimTypeNames):
  var p = alloc(16)
  let (allocs, deallocs) = getMemCounters()
  echo allocs > deallocs  # выводит true — dealloc ещё не вызван
  dealloc(p)
```

---

### 7. `ptrSize`

```nim
proc ptrSize(p: pointer): int
```

**Что делает.** Возвращает реальный полезный размер блока, на который
указывает `p` — он может быть **больше** запрошенного изначально
размера из-за округления до класса размера ячейки (для маленьких
чанков) или до размера страницы (для больших чанков). Именно поэтому
`realloc` может дать доступ к дополнительным байтам "бесплатно", если
округление в исходном `alloc` было щедрее, чем требовалось.

- **Параметры**:
  - `p: pointer` — указатель, ранее полученный от `alloc`/`alloc0`.

- **Примеры**:

```nim
var p = alloc(1)
echo ptrSize(p) >= 1  # выводит true — реальный размер не меньше запрошенного
dealloc(p)
```

## V. Возврат страниц операционной системе

### 1. `deallocOsPages`

```nim
proc deallocOsPages()
```

**Что делает.** Освобождает операционной системе **все** страницы,
удерживаемые кучей текущего потока, вне зависимости от того, заняты они
живыми объектами или нет. Вызывается на завершении работы потока/
программы, а не в процессе обычной работы: после вызова любое
обращение к ранее выделенной в этой куче памяти становится
неопределённым поведением.

- **Параметры**: нет.

- **Примеры**:

```nim
proc workerThreadShutdown() =
  # ... завершение работы, все объекты в этой куче уже не нужны ...
  deallocOsPages()
```

## VI. Как это устроено внутри (сводный обзор)

Публичные процедуры разделов II–III в конечном счёте сводятся к двум
внутренним операциям — `rawAlloc`/`rawDealloc` — которые решают, по
какому из трёх путей пойти, в зависимости от размера запроса:

- **Маленький блок** (помещается в `SmallChunk`) обслуживается почти
  без арифметики: если у активного чанка нужного класса размера есть
  свободные ячейки — берётся голова списка; если ячеек нет, но есть
  место в "аккумуляторе" — сдвигается указатель-аккумулятор. Оба пути —
  O(1). Только когда подходящего чанка вообще нет, запрашивается новый
  чанк у механизма больших блоков.
- **Большой блок** ищется в TLSF-матрице `a.matrix[fl][sl]` — двумерной
  таблице, где `fl`/`sl` ("first level"/"second level" индексы) находятся
  почти мгновенно через побитовые операции над `flBitmap`/`slBitmap`
  (позиция первого установленного бита), без перебора списков. Если
  подходящего чанка нет — запрашиваются новые страницы у ОС, а лишний
  остаток режется (`splitChunk`) и кладётся обратно в матрицу.
- **Огромный блок** (больше `HugeChunkSize`) выделяется и освобождается
  напрямую через ОС, минуя матрицу совсем — такие блоки слишком редки и
  велики, чтобы их стоило кешировать.

При освобождении больших блоков соседние свободные чанки **сливаются**
(coalescing) в один — это защищает от фрагментации кучи ценой
дополнительной проверки соседей слева и справа при каждом `dealloc`.

Учёт того, где начинается каждый большой чанк, ведётся в двух
структурах: `IntSet` (битовый набор адресов начал чанков — быстрая
проверка "является ли этот адрес началом чанка") и AVL-дерево
интервалов (быстрый поиск "какому чанку принадлежит указатель внутри
диапазона", нужен для проверки внутренних/interior-указателей сборщиком
мусора).

Для разделяемой кучи между потоками добавляется ещё один слой: вместо
немедленной блокировки при освобождении "чужого" блока (выделенного не
текущим потоком) операция часто просто кладёт блок в lock-free список
отложенного освобождения владельца — фактическое освобождение происходит
позже, когда владелец сам обращается к аллокатору.

## VII. Практические рецепты

### 1. Пул объектов фиксированного размера

```nim
type
  Particle = object
    x, y, vx, vy: float32

proc newParticlePool(capacity: int): ptr UncheckedArray[Particle] =
  # alloc0 гарантирует нулевые скорости/координаты для всех частиц сразу.
  result = cast[ptr UncheckedArray[Particle]](
    alloc0(capacity * sizeof(Particle)))

proc freeParticlePool(pool: ptr UncheckedArray[Particle]) =
  dealloc(pool)

var pool = newParticlePool(1000)
pool[0].x = 5.0
echo pool[0].x, " ", pool[1].x  # выводит 5.0 0.0
freeParticlePool(pool)
```

### 2. Растущий буфер (аналог `seq`) через `realloc`

```nim
type GrowBuffer = object
  data: ptr UncheckedArray[byte]
  len, cap: int

proc push(buf: var GrowBuffer, b: byte) =
  if buf.len >= buf.cap:
    # Рост с запасом (удвоение), чтобы не платить за realloc на каждый push:
    let newCap = max(8, buf.cap * 2)
    buf.data = cast[ptr UncheckedArray[byte]](realloc(buf.data, newCap))
    buf.cap = newCap
  buf.data[buf.len] = b
  inc buf.len

proc destroy(buf: var GrowBuffer) =
  dealloc(buf.data)
  buf.len = 0
  buf.cap = 0

var buf = GrowBuffer(data: alloc(8), len: 0, cap: 8)
for i in 0 ..< 20:
  push(buf, byte(i))
echo buf.len, " ", buf.cap  # выводит 20 32 — ёмкость выросла удвоением
destroy(buf)
```

---

### 3. Передача буфера между потоками через `allocShared`

```nim
# Буфер выделяется в главном потоке, но освобождается тем потоком,
# который закончил с ним работать — это допустимо только для
# памяти из allocShared/deallocShared, не для обычного alloc/dealloc.
proc makeSharedPayload(size: int): pointer =
  result = allocShared0(size)

proc consumeAndFree(p: pointer) {.thread.} =
  # ... обработка данных в дочернем потоке ...
  deallocShared(p)  # безопасно, даже если выделено в другом потоке

var payload = makeSharedPayload(4096)
var worker: Thread[pointer]
createThread(worker, consumeAndFree, payload)
joinThread(worker)
```

### 4. Мониторинг потребления памяти

```nim
proc logMemoryUsage(tag: string) =
  echo tag, ": occupied=", getOccupiedMem(),
       " total=", getTotalMem(),
       " peak=", getMaxMem()

logMemoryUsage("до выделения")
var buffers: seq[pointer]
for i in 0 ..< 100:
  buffers.add(alloc(4096))
logMemoryUsage("после выделения")
for p in buffers:
  dealloc(p)
logMemoryUsage("после освобождения")
```

## IX. Сводка: какую процедуру выбрать

- Нужно выделить память, которой будет пользоваться только текущий
  поток → `alloc` (или `alloc0`, если важно нулевое начальное состояние).
- Нужно освободить такую память → `dealloc`.
- Нужно изменить размер уже выделенного блока, сохранив данные →
  `realloc`; если важно ещё и обнулить прирост — `realloc0`.
- Нужно передать буфер в другой поток или освободить его не тем
  потоком, который выделял → используйте пару `allocShared`/
  `deallocShared` вместо `alloc`/`dealloc` с самого начала.
- Нужно логировать/ограничивать потребление памяти → `getOccupiedMem`
  для текущего значения, `getMaxMem` для исторического пика,
  `getFreeMem`/`getTotalMem` для деталей кучи.
- Нужно узнать, сколько байт реально доступно по указателю (не только
  запрошенных) → `ptrSize`.
- Нужно полностью освободить память потока перед его завершением →
  `deallocOsPages` (после этого вызова использовать старые указатели
  этой кучи нельзя).
- Нужно разобраться, как работает сам механизм выбора чанка/слияния/
  поиска по TLSF-матрице → раздел VI, а не отдельные процедуры этого
  справочника — это внутренняя механика, не публичный API.
