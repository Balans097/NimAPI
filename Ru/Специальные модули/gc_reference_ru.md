# gc.nim — справочник модуля

> **Импорт:** отдельно не импортируется — файл `lib/system/gc.nim` подключается
> директивой `include` прямо в модуль `system` при компиляции с бэкенд-сборщиком
> мусора `refc`. Пользовательский код обращается только к небольшому набору
> процедур `GC_*`, которые становятся доступны автоматически (система `system`
> импортируется неявно во все программы на Nim).
> **Область применения:** рантайм-реализация сборщика мусора Nim по схеме
> *Deferred Reference Counting* (отложенный подсчёт ссылок) с фоновым
> детектором циклов через mark&sweep.

> **Важное замечание об этом справочнике.** В отличие от `std/algorithm`,
> `gc.nim` — это не библиотечный модуль с публичным API, а внутренняя часть
> рантайма компилятора. Подавляющее большинство процедур здесь либо
> `{.compilerproc.}` (вызываются только сгенерированным C-кодом), либо просто
> не экспортированы (без `*`) и работают с приватными типами `PCell`/`GcHeap`
> через указатели со смещением заголовка. Написать для них «типичный вызов
> пользователя» невозможно — такого вызова не существует в природе. Поэтому:
> - для процедур **публичного API** (раздел VI) ниже приведены настоящие,
>   рабочие примеры кода — так, как их писал бы обычный пользователь Nim;
> - для **внутренних механизмов** (разделы II–V) вместо «примеров вызова»
>   даны **трассировки алгоритма** — пошаговая иллюстрация того, что
>   происходит внутри GC при работе программы (создание объекта, `x = y`,
>   выход из области видимости и т.п.). Это не код, который можно запустить
>   отдельно, а разбор того, что реально исполняется под капотом обычной
>   программы.

Основная идея модуля: каждая *ячейка* (cell) — это заголовок с полем
`refcount` и указателем на тип, размещённый прямо перед пользовательскими
данными (перед `ref`, `seq` или `string`). Присваивания ссылок увеличивают и
уменьшают `refcount` через `incRef`/`decRef`. Ячейки, чей счётчик упал до нуля,
попадают в ZCT (*zero count table*) и освобождаются пачками. Поскольку чистый
подсчёт ссылок не ловит циклические ссылки, поверх него работает
периодический mark&sweep («cycle collector»), который помечает достижимые из
стека и глобальных переменных объекты и подчищает всё недостижимое.

## I. Типы и глобальное состояние

### `WalkOp`

```nim
type
  WalkOp = enum
    waMarkGlobal,    # часть резервного/отладочного mark&sweep
    waMarkPrecise,   # часть резервного/отладочного mark&sweep
    waZctDecRef, waPush
```

**Что делает.** Перечисление кодов операции, которую нужно выполнить с
дочерней ссылкой при обходе объекта. Одна и та же функция обхода
(`forAllChildren`) используется и для decref при удалении из ZCT, и для
пометки при поиске циклов — конкретное действие передаётся именно через это
перечисление, а не через отдельные функции обхода для каждого случая.

**Разбор реализации.** Это классический приём «один обходчик графа — много
операций»: вместо четырёх copy-paste версий обхода дерева полей объекта
(`forAllChildrenAux`, `forAllSlotsAux`) существует одна версия, которая в
конце просто делает `case op` (см. `doOperation`) и решает, что сделать с
найденной дочерней ссылкой — уменьшить refcount (`waZctDecRef`), положить в
очередь на пометку (`waPush`/`waMarkPrecise`) или пометить рекурсивно сразу
(`waMarkGlobal`).

**Список значений:**
- `waMarkGlobal` — пометить достижимый объект немедленно (используется при
  обходе глобальных переменных и дополнительных корней);
- `waMarkPrecise` — не помечать сразу, а положить в `tempStack` (устраняет
  глубокую рекурсию при обходе больших графов);
- `waZctDecRef` — уменьшить refcount дочернего объекта (когда родитель
  освобождается из ZCT);
- `waPush` — просто добавить ячейку в `tempStack` без пометки.

### `GcHeap` и `gch`

```nim
type
  GcHeap {.final, pure.} = object
    stack: GcStack
    cycleThreshold: int
    zctThreshold: int
    zct: CellSeq             # таблица нулевого счётчика (zero count table)
    decStack: CellSeq        # ячейки стека, которые нужно декрефнуть повторно
    tempStack: CellSeq       # временный стек для устранения рекурсии
    recGcLock: int           # блокировка рекурсии через финалайзеры
    region: MemRegion        # управляемая GC область памяти
    stat: GcStat
    marked: CellSet
    additionalRoots: CellSeq # фиктивные корни для GC_ref/unref
    gcThreadId: int

var
  gch {.rtlThreadVar.}: GcHeap
```

**Что делает.** `GcHeap` — это всё состояние сборщика мусора для одного
потока: пороги срабатывания, три вспомогательных списка ячеек (ZCT, стек
декрефа, временный стек обхода), множество помеченных ячеек и собственная
управляемая область памяти (`MemRegion`). Переменная `gch` — глобальный
(точнее, потоко-локальный — `{.rtlThreadVar.}`) экземпляр этого состояния;
почти все процедуры файла читают и изменяют именно её.

**Разбор реализации.** Разделение на `zct` / `decStack` / `tempStack` — не
случайность, а способ избежать глубокой рекурсии на больших графах объектов:
там, где наивная реализация вызвала бы себя рекурсивно для каждого дочернего
поля, здесь дочерние ячейки складываются в массив (`tempStack`), и цикл `while`
разбирает его итеративно (см. `markS`). Поле `recGcLock` — счётчик вложенных
`GC_disable()`; пока он больше нуля, `collectCT` не запускает сборку — это
защищает от повторного входа в сборщик мусора изнутри финалайзера.

**Список ключевых полей:**
- `zct: CellSeq` — очередь ячеек с обнулившимся refcount, ожидающих
  освобождения;
- `decStack: CellSeq` — ячейки, найденные на стеке при последнем сканировании,
  для которых нужно откатить временный incref;
- `cycleThreshold: int` / `zctThreshold: int` — пороги занятой памяти и
  размера ZCT, при превышении которых запускается очередная фаза сборки;
- `marked: CellSet` — множество ячеек, помеченных как достижимые в текущем
  проходе mark&sweep;
- `recGcLock: int` — счётчик вложенных вызовов `GC_disable()`.

### Битовые поля `refcount` (цвет ячейки)

```nim
const
  rcIncrement = 0b1000 # чтобы младшие 3 бита не трогались
  rcBlack = 0b000  # ячейка чёрная: используется или свободна
  rcGray = 0b001   # возможный член цикла
  rcWhite = 0b010  # член мусорного цикла
  rcPurple = 0b011 # возможный корень цикла
  ZctFlag = 0b100  # ячейка в ZCT
  rcShift = 3      # сдвиг, чтобы получить сам счётчик ссылок
  colorMask = 0b011

template color(c): untyped = c.refCount and colorMask
template setColor(c, col) =
  when col == rcBlack:
    c.refcount = c.refcount and not colorMask
  else:
    c.refcount = c.refcount and not colorMask or col
```

**Что делает.** Поле `refcount` каждой ячейки хранит сразу две вещи в одном
машинном слове: сам счётчик ссылок (в старших битах, начиная со сдвига
`rcShift`) и «цвет»/флаг в трёх младших битах. Это классическая
битовая упаковка ради экономии памяти — заводить отдельное поле `color: byte`
на каждую ячейку было бы расточительно.

**Разбор реализации.** `rcIncrement = 0b1000` подобран так, чтобы прибавление
или вычитание единицы счётчика (`c.refcount +% rcIncrement`) никогда не
затрагивало три младших бита — они изменяются только явно, через
`setColor`/`ZctFlag`. Цвета `rcBlack/rcGray/rcWhite/rcPurple` в этом файле
объявлены, но активно используются только в отладочном/альтернативном
mark&sweep (см. `when false` блоки) — в боевом пути основной цикл различает
только «есть флаг `ZctFlag`» или нет.

**Список констант:**
- `rcIncrement` — величина одного `incref`/`decref` в единицах `refcount`;
- `ZctFlag` — бит «ячейка сейчас находится в ZCT»;
- `rcShift` — сколько бит нужно сдвинуть `refcount`, чтобы получить настоящее
  число ссылок (`internRefcount`);
- `colorMask` — маска для извлечения/установки трёхбитного цвета.

## II. Подсчёт ссылок

### `incRef` / `decRef`

```nim
proc incRef(c: PCell) {.inline.}
proc decRef(c: PCell) {.inline.}
```

**Что делает.** `incRef` увеличивает счётчик ссылок ячейки на `rcIncrement`.
`decRef` уменьшает его и, если результат опустился ниже `rcIncrement` (то
есть логический счётчик достиг нуля), кладёт ячейку в ZCT через `rtlAddZCT` —
физическое освобождение памяти в этот момент ещё не происходит, оно отложено
до `collectZCT`.

**Разбор реализации.** Именно эта отложенность и даёт название алгоритму
*Deferred* Reference Counting: `decRef` — это O(1) операция без побочных
рекурсивных вызовов, в отличие от «наивного» refcounting, где `decRef` сразу
рекурсивно декрефал бы все дочерние объекты. Здесь глубокая работа переносится
в `collectZCT`, где её проще пакетировать и (при `withRealTime`) прервать по
таймауту.

**Список параметров:**
- `c: PCell` — указатель на заголовок ячейки (не на пользовательские данные —
  для конвертации служат `usrToCell`/`cellToUsr`).

**Трассировка** (что происходит при `a = b`, где `a`, `b: ref T`):

```nim
# Псевдо-C, который генерирует компилятор для "a = b":
# asgnRef(addr a, cast[pointer](b))
#
# Внутри asgnRef:
#   1. incRef(usrToCell(b))   # у b стало на одну ссылку больше
#   2. decRef(usrToCell(a))   # старое значение a теряет одну ссылку
#      # если после этого refcount(a_старое) достиг 0 —
#      # ячейка попадает в ZCT и будет освобождена позже, в collectZCT
#   3. a = b                  # сам указатель переприсваивается
```

### `asgnRef`

```nim
proc asgnRef(dest: PPointer, src: pointer) {.compilerproc, inline.}
```

**Что делает.** Это и есть та самая процедура, которую генерируемый компилятором
C-код вызывает на каждое присваивание ссылочного значения (`ref`, `seq`,
`string`) в куче. Обновляет счётчики ссылок у старого и нового значения и
только затем выполняет само присваивание указателя.

**Разбор реализации.** Порядок операций специально зафиксирован комментарием
в исходнике («BUGFIX: first incRef then decRef!») — сначала инкремент нового
значения, потом декремент старого. Если бы порядок был обратным и `dest`
случайно совпадал с `src` (то есть `a = a`), декремент мог бы преждевременно
обнулить единственную ссылку на объект прежде, чем инкремент восстановит
счётчик, — и он был бы ошибочно помещён в ZCT.

**Список параметров:**
- `dest: PPointer` — адрес поля-указателя, в которое пишем (гарантированно не
  на стеке — это проверяет `gcAssert(not isOnStack(dest), ...)`);
- `src: pointer` — новое значение (может быть `nil`).

---

### `unsureAsgnRef`

```nim
proc unsureAsgnRef(dest: PPointer, src: pointer) {.compilerproc.}
```

**Что делает.** Вариант `asgnRef` для случаев, когда компилятор *не может
статически определить*, лежит ли `dest` на стеке или в куче — это происходит
при `var`-параметрах (см. пример из вводного комментария файла: `setRef(r)`
против `setRef(r.left)`). Счётчики обновляются, только если во время
выполнения окажется, что `dest` не на стеке.

**Разбор реализации.** Ссылки на стеке в этом сборщике вообще не подсчитываются
(ради производительности — таков основной компромисс алгоритма, заявленный в
шапке файла), поэтому обновлять refcount для стекового адреса было бы не
просто лишним, а неверным. Проверка `isOnStack` дешева на большинстве систем
с непрерывным стеком — это два сравнения указателя с границами стека.

**Список параметров:**
- `dest: PPointer` — адрес назначения, для которого неизвестно на этапе
  компиляции, стек это или куча;
- `src: pointer` — новое значение.

---

### `nimGCref` / `nimGCunref`

```nim
proc nimGCref(p: pointer) {.compilerproc.}
proc nimGCunref(p: pointer) {.compilerproc.}
```

**Что делает.** Это рантайм-реализация процедур `GC_ref`/`GC_unref` из
публичного API `system`: добавляет объект в список `additionalRoots` («корни
снаружи») и повышает его refcount так, чтобы объект не собирался, даже если
на него нет обычных ссылок — например, объект хранится только в C-массиве.
`nimGCunref` убирает объект из `additionalRoots` и снимает эту искусственную
ссылку.

**Что делает на границах.** `nimGCunref` линейно ищет ячейку в
`additionalRoots` и, если находит, заменяет её последним элементом списка
(классический трюк «swap-with-last» для удаления из неупорядоченного массива
за O(1) без сдвига хвоста).

**Список параметров:**
- `p: pointer` — указатель на пользовательские данные (не на заголовок ячейки;
  внутри вызывается `usrToCell(p)`).

## III. Выделение объектов

### `rawNewObj` / `newObj` / `newObjNoInit`

```nim
proc rawNewObj(typ: PNimType, size: int, gch: var GcHeap): pointer
proc newObj(typ: PNimType, size: int): pointer {.compilerRtl, noinline, raises: [].}
proc newObjNoInit(typ: PNimType, size: int): pointer {.compilerRtl, raises: [].}
```

**Что делает.** `rawNewObj` — сердце распределителя: перед выделением
проверяет пороги и, если нужно, запускает сборку (`collectCT`), затем реально
выделяет память под заголовок ячейки плюс пользовательские данные, обнуляет
поле `refcount`, ставит флаг `ZctFlag` (счётчик равен нулю, но ячейка ещё
жива до первого присваивания) и сразу же кладёт ячейку в ZCT. `newObj`
дополнительно зануляет пользовательские данные (`zeroMem`); `newObjNoInit` —
более быстрый вариант без зануления, для мест, где инициализация и так
произойдёт сразу следом.

**Разбор реализации.** Обратите внимание на порядок: `collectCT(gch)`
вызывается *до* выделения, а не после — то есть решение о сборке мусора
принимается по состоянию кучи, актуальному на момент запроса, а не задним
числом. Новый объект сразу попадает в ZCT с `refcount = 0` — это позволяет
единообразно обращаться с «ещё ничему не присвоенным» объектом так же, как с
объектом, чей счётчик действительно упал до нуля: оба пути освобождения
проходят через один и тот же `collectZCT`.

**Список параметров:**
- `typ: PNimType` — RTTI-дескриптор типа (нужен для последующего обхода
  дочерних ссылок сборщиком);
- `size: int` — размер пользовательских данных в байтах (без учёта заголовка
  ячейки — `sizeof(Cell)` прибавляется внутри);
- `gch: var GcHeap` — куча, в которой производится выделение (в
  однопоточном варианте почти всегда глобальная `gch`).

**Трассировка** (создание `ref T` в пользовательском коде):

```nim
# Пользовательский код:
#   var r = new(T)
#
# Компилятор генерирует примерно:
#   r = newObj(T_typeInfo, sizeof(T))
#
# Внутри newObj -> rawNewObj:
#   1. collectCT(gch)                 # возможно, срабатывает фоновая сборка
#   2. rawAlloc(...)                  # реальное выделение памяти
#   3. res.refcount = ZctFlag         # счётчик = 0, но помечена как "в ZCT"
#   4. addNewObjToZCT(res, gch)       # добавление в очередь на "первую сборку"
#   5. result = cellToUsr(res)        # пользователю возвращается адрес ПОСЛЕ заголовка
```

### `newObjRC1` / `newSeqRC1`

```nim
proc newObjRC1(typ: PNimType, size: int): pointer {.compilerRtl, noinline, raises: [].}
proc newSeqRC1(typ: PNimType, len: int): pointer {.compilerRtl, raises: [].}
```

**Что делает.** Оптимизированный вариант выделения для случая, когда
компилятор статически знает, что созданный объект будет немедленно присвоен
ровно одной ссылке (типичный случай `var x = ...`). В этом случае можно сразу
поставить `refcount = 1` и вообще не класть объект в ZCT — экономится один
цикл «положить в ZCT → тут же убрать при первом присваивании».

**Разбор реализации.** Это пример оптимизации на основе анализа потока
данных компилятором: обычный `newObj` пессимистично предполагает, что новый
объект может какое-то время «повисеть» без ссылок (например, быть возвращён
из процедуры и не сохранён вызывающей стороной), поэтому обязан пройти через
ZCT. `newObjRC1` используется только там, где такой анализ доказал, что
ровно одно присваивание последует немедленно.

**Список параметров:**
- `typ: PNimType` — дескриптор типа;
- `size` / `len: int` — размер в байтах (`newObjRC1`) или длина
  последовательности (`newSeqRC1`).

---

### `growObj`

```nim
proc growObj(old: pointer, newsize: int, gch: var GcHeap): pointer
```

**Что делает.** Реализация роста `seq`/`string` при добавлении элементов сверх
текущей вместимости: выделяет новый, больший блок, копирует туда старые данные
и хвост зануляет. Старая ячейка не освобождается немедленно — её длина просто
обнуляется (`cast[PGenericSeq](old).len = 0`), чтобы сборщик мусора не пытался
пройтись по «украденным» дочерним ссылкам дважды.

**Разбор реализации.** Копирование `oldsize + sizeof(Cell)` одним `copyMem`
захватывает сразу и заголовок ячейки (тип, счётчик и т.д.), и все данные —
это надёжнее, чем копировать поля по отдельности, потому что автоматически
переносит любые будущие поля заголовка без правки этого кода. Обнуление
длины старого объекта — это защита от двойного обхода: если бы GC успел
просканировать старую ячейку до её физического освобождения, он бы увидел в
ней те же дочерние указатели, что и в новой, и учёл бы их дважды.

**Список параметров:**
- `old: pointer` — указатель на пользовательские данные старой
  последовательности/строки;
- `newsize: int` — новый требуемый размер в байтах;
- `gch: var GcHeap` — используемая куча.

## IV. Обход графа объектов

### `forAllChildren` / `forAllChildrenAux`

```nim
proc forAllChildren(cell: PCell, op: WalkOp)
proc forAllChildrenAux(dest: pointer, mt: PNimType, op: WalkOp)
```

**Что делает.** `forAllChildren` для одной ячейки находит все её дочерние
ссылки (поля-`ref`, элементы `seq`, поля объектов и кортежей) и для каждой
выполняет операцию `op` (см. `WalkOp`). Если у типа есть собственный маркер
(`cell.typ.marker` — сгенерированная компилятором функция обхода конкретно
для этого типа), используется он; иначе — универсальный обход через RTTI
(`forAllChildrenAux`/`forAllSlotsAux`), рекурсивно спускающийся по дереву
полей: объекты и кортежи — по списку слотов, массивы — поэлементно,
`ref`/`seq`/`string` — как лист дерева, на котором вызывается операция.

**Разбор реализации.** Тип с `ntfNoRefs` в `mt.flags` (нет ни одного
GC-указателя внутри) пропускается целиком без спуска в его поля — важная
оптимизация: обход не тратит время на структуры, заведомо не содержащие
ссылок.

**Список параметров:**
- `cell: PCell` / `dest: pointer` — ячейка или сырой адрес данных, которые
  обходим;
- `mt: PNimType` — RTTI-дескриптор типа этих данных;
- `op: WalkOp` — что сделать с каждой найденной дочерней ссылкой.

---

### `markS` / `markGlobals`

```nim
proc markS(gch: var GcHeap, c: PCell)
proc markGlobals(gch: var GcHeap) {.raises: [].}
```

**Что делает.** `markS` помечает ячейку `c` как достижимую (кладёт в
`gch.marked`) и итеративно (через `tempStack`, а не рекурсивно) обходит и
помечает всё, что достижимо из неё. `markGlobals` — точка входа для пометки
«внешних» корней: глобальных переменных программы (`globalMarkers`/
`threadLocalMarkers` — списки функций-маркеров, которые генерирует
компилятор по одной на модуль) и объектов, добавленных вручную через
`GC_ref` (`additionalRoots`).

**Разбор реализации.** Использование явного стека (`tempStack`) вместо
рекурсивных вызовов `forAllChildren` — сознательное решение против
переполнения системного стека на глубоких структурах данных (длинный связный
список, глубокое дерево). Классическая техника «устранения рекурсии»: вместо
`markChild(x)` внутри тела функции — `add(tempStack, x)`, и внешний `while`
разбирает накопленное.

**Список параметров:**
- `gch: var GcHeap` — куча, содержащая множество `marked` и вспомогательный
  `tempStack`;
- `c: PCell` — корень, с которого начинается пометка (для `markS`).

---

### `gcMark` / `markStackAndRegisters`

```nim
proc gcMark(gch: var GcHeap, p: pointer) {.inline.}
proc markStackAndRegisters(gch: var GcHeap) {.noinline, cdecl.}
```

**Что делает.** `markStackAndRegisters` сканирует весь текущий стек вызовов (и
регистры, сохранённые при входе в функцию) в поисках значений, похожих на
указатели на кучу GC, вызывая `gcMark` для каждого потенциального адреса.
`gcMark` проверяет, указывает ли адрес `p` действительно внутрь
GC-управляемого объекта (`interiorAllocatedPtr`), и если да — временно
инкрефит его и запоминает в `decStack`, чтобы после сканирования стека вернуть
счётчик обратно (см. `unmarkStackAndRegisters`).

**Что делает на границах.** Стек сканируется консервативно: любое машинное
слово, похожее на адрес внутри кучи GC, трактуется как потенциальная ссылка,
даже если на самом деле это, например, случайно похожее на указатель целое
число — отсюда и название «консервативный сборщик» применительно к
сканированию стека. Ложные срабатывания безопасны (объект просто лишний раз
не соберётся в этом цикле), пропуски — нет, поэтому алгоритм соглашается на
избыточную осторожность.

**Список параметров:**
- `gch: var GcHeap` — куча с полями `stack`, `decStack`;
- `p: pointer` — потенциальный адрес-кандидат, найденный при сканировании
  стека (для `gcMark`).

## V. Цикл сборки мусора

### `collectZCT`

```nim
proc collectZCT(gch: var GcHeap): bool
```

**Что делает.** Разбирает таблицу нулевого счётчика (ZCT): для каждой ячейки
с `refcount`, реально равным нулю, вызывает финалайзер (если есть), рекурсивно
декрефает всех её детей (через `forAllChildren(c, waZctDecRef)` — что может
добавить в ZCT новые ячейки прямо во время работы этой же функции) и
физически освобождает память. Возвращает `false`, только если сборка была
прервана по таймауту в режиме `withRealTime` (см. «мягкий реал-тайм» ниже).

**Разбор реализации.** Ячейка забирается не с начала и не с конца списка, а
всегда с индекса `0`, после чего на её место переносится последний элемент
(`gch.zct.d[0] = gch.zct.d[L-1]`) — снова приём «swap-with-last» для удаления
из массива за O(1) без сдвига остальных элементов. Комментарий в исходнике
прямо предупреждает: поскольку освобождение одной ячейки может добавить в ZCT
её детей, это фактически «глубокое» освобождение, и весь смысл
пакетирования (`workPackage = 100`) — не дать этой цепочке освобождений
заблокировать поток слишком надолго в режиме с ограничением по времени.

**Список параметров:**
- `gch: var GcHeap` — куча с полем `zct` и (при `withRealTime`) `maxPause`.

---

### `collectCTBody` / `collectCT`

```nim
proc collectCTBody(gch: var GcHeap) {.raises: [].}
proc collectCT(gch: var GcHeap)
```

**Что делает.** `collectCT` — это «привратник»: проверяет, превышены ли
пороги (`zctThreshold` для ZCT или `cycleThreshold` для занятой памяти) и не
удерживается ли `recGcLock`, и только тогда вызывает `collectCTBody`.
`collectCTBody` — собственно одна полная фаза сборки: сканирует стек,
собирает ZCT и, если после этого объём занятой памяти всё ещё превышает
`cycleThreshold`, дополнительно запускает поиск циклов (`collectCycles`).

**Разбор реализации.** Порог цикловой сборки после каждого запуска
пересчитывается адаптивно: `cycleThreshold = max(InitialCycleThreshold,
occupiedMem * CycleIncrease)` — то есть следующий поиск циклов состоится не
раньше, чем занятая память вырастет в `CycleIncrease` (2) раза от текущей.
Это балансирует между «искать циклы слишком часто» (дорого) и «никогда не
искать» (утечка памяти на циклических структурах).

**Список параметров:**
- `gch: var GcHeap` — куча целиком (пороги, ZCT, статистика).

---

### `collectCycles` / `sweep`

```nim
proc collectCycles(gch: var GcHeap) {.raises: [].}
proc sweep(gch: var GcHeap)
```

**Что делает.** `collectCycles` — полный проход поиска циклических мусорных
структур: сначала дочищает ZCT (чтобы «цвет» ZCT не путался с пометкой),
сбрасывает множество `marked`, помечает как достижимое всё, что видно со
стека (`decStack`) и из глобальных переменных (`markGlobals`), а затем
вызывает `sweep`, который проходит **по всем объектам в управляемой области
памяти** и освобождает те, что не попали в `marked`.

**Что делает на границах.** Объект, который не помечен, но при этом всё ещё
несёт флаг `ZctFlag` (это может случиться, если он был создан прямо во время
работы финалайзера), не освобождается физически — с него только снимается
флаг, чтобы не потерять его в следующем цикле.

**Список параметров:**
- `gch: var GcHeap` — куча (используются `zct`, `marked`, `decStack`,
  `region`).

---

## VI. Публичный API управления GC

Ниже — процедуры, которые *действительно* можно вызвать из обычной программы
на Nim (они доступны напрямую, без явного `import`, как часть модуля
`system`). Примеры в этом разделе — рабочий, запускаемый код.

### `GC_disable` / `GC_enable`

```nim
proc GC_disable()
proc GC_enable()
```

**Что делает.** `GC_disable` временно приостанавливает работу сборщика:
увеличивает счётчик вложенности `recGcLock`, из-за чего `collectCT` перестаёт
запускать сборку, даже если пороги превышены. `GC_enable` уменьшает этот
счётчик обратно; вызовы могут быть вложенными (два `GC_disable` требуют двух
`GC_enable`).

**Список параметров:** без параметров.

**Пример:**

```nim
proc criticalSection() =
  GC_disable()
  var buf = newSeq[byte](1024)
  # здесь гарантированно не произойдёт паузы на сборку мусора
  for i in 0..<len(buf):
    buf[i] = byte(i mod 256)
  GC_enable()
  echo "готово, длина буфера: ", len(buf) # выводит "готово, длина буфера: 1024"
```

---

### `GC_fullCollect`

```nim
proc GC_fullCollect()
```

**Что делает.** Принудительно запускает полный цикл сборки, включая поиск
циклов, независимо от текущих порогов — временно обнуляет
`cycleThreshold`, вызывает `collectCT`, затем восстанавливает прежний порог.

**Список параметров:** без параметров.

**Пример:**

```nim
type
  Node = ref object
    next: Node

var a = Node()
var b = Node()
a.next = b
b.next = a       # искусственный цикл ссылок
a = nil
b = nil          # обычный подсчёт ссылок не освободит эту пару сам по себе
GC_fullCollect()  # принудительно находит и собирает цикл
echo "цикл обработан"  # выводит "цикл обработан"
```

---

### `GC_enableMarkAndSweep` / `GC_disableMarkAndSweep`

```nim
proc GC_enableMarkAndSweep()
proc GC_disableMarkAndSweep()
```

**Что делает.** Включает или выключает именно фазу поиска циклов
(mark&sweep), не трогая обычный подсчёт ссылок. `GC_disableMarkAndSweep`
выставляет `cycleThreshold` в максимально возможное значение, из-за чего
условие «пора искать циклы» практически никогда не выполняется.

**Разбор реализации.** Это не полная остановка GC (как `GC_disable`) — обычные
объекты без циклов продолжают освобождаться через ZCT как обычно; отключается
только более дорогая проверка на циклические структуры.

**Список параметров:** без параметров.

**Пример:**

```nim
GC_disableMarkAndSweep()
# в этом участке программы циклические ссылки НЕ будут находиться и
# освобождаться, но обычные, ациклические объекты продолжают собираться
GC_enableMarkAndSweep()
echo "поиск циклов снова включён" # выводит "поиск циклов снова включён"
```

---

### `GC_getStatistics`

```nim
proc GC_getStatistics(): string
```

**Что делает.** Возвращает многострочную сводку по состоянию сборщика:
суммарную и занятую память, число сканирований стека, максимальное число
ячеек на стеке, число полных сборок циклов, максимальный использованный
порог, вместимость ZCT и, при включённом `withRealTime`, максимальную
зафиксированную паузу.

**Список параметров:** без параметров.

**Пример:**

```nim
echo GC_getStatistics()
# выводит примерно:
# [GC] total memory: 1048576
# [GC] occupied memory: 32768
# [GC] stack scans: 12
# [GC] stack cells: 4
# [GC] cycle collections: 1
# [GC] max threshold: 4194304
# [GC] zct capacity: 512
# [GC] max cycle table size: 0
# [GC] max pause time [ms]: 0
```

---

### `GC_step` / `GC_setMaxPause`

```nim
proc GC_setMaxPause(MaxPauseInUs: int)
proc GC_step(us: int, strongAdvice = false, stackSize = -1) {.noinline.}
```

**Что делает.** Обе процедуры доступны только когда рантайм собран с
`-d:useRealtimeGC`. `GC_setMaxPause` задаёт глобальный лимит длительности
одной паузы на сборку в микросекундах — при его превышении `collectZCT`
досрочно прервётся и продолжит с того же места на следующем шаге.
`GC_step` явно выполняет один «шаг» сборки длиной не более `us` микросекунд;
`strongAdvice = true` заставляет выполнить шаг, даже если обычные пороги ещё
не превышены — то есть это ручное управление тем, «когда» тратится время на
GC, вместо того чтобы ждать автоматического срабатывания посреди кадра.

**Список параметров:**
- `MaxPauseInUs: int` — предельная длительность одной паузы, микросекунды
  (для `GC_setMaxPause`);
- `us: int` — бюджет времени на этот конкретный шаг, микросекунды;
- `strongAdvice: bool` — выполнить шаг, даже если пороги ещё не достигнуты;
- `stackSize: int` — если ≥ 0, временно ограничивает сканируемую часть
  стека этим размером (типичный сценарий: игровой цикл, вызывающий `GC_step`
  каждый кадр между отрисовками).

**Пример** (типичный игровой/интерактивный цикл):

```nim
GC_setMaxPause(1_000) # не более 1 мс на одну паузу сборки
while running:
  updateGame()
  renderFrame()
  GC_step(1_000, strongAdvice = true) # отдаём сборщику маленький бюджет
                                       # времени каждый кадр вместо одной
                                       # большой паузы где-то посередине
```

## VII. Практические рецепты

### 1. Диагностика утечек через статистику GC

```nim
proc reportBefore() =
  echo "до операции:"
  echo GC_getStatistics()

proc heavyOperation() =
  var data = newSeq[seq[int]](1000)
  for i in 0..<len(data):
    data[i] = newSeq[int](1000)
  discard data

reportBefore()
heavyOperation()
GC_fullCollect() # прогоняем полный цикл, чтобы статистика была честной
echo "после операции и полной сборки:"
echo GC_getStatistics()
```

Сравнение `occupied memory` до и после `GC_fullCollect()` в двух похожих
точках программы — самый простой способ заметить, что память не
возвращается сборщику (характерный признак циклических ссылок, которые
почему-то не находятся, либо ссылок, случайно удерживаемых глобальным
состоянием).

### 2. Отключение GC на время критического участка

```nim
proc renderAudioBuffer(samples: int): seq[float32] =
  GC_disable()          # ни одна пауза GC не должна прервать этот расчёт
  result = newSeq[float32](samples)
  for i in 0..<samples:
    result[i] = float32(i) / float32(samples)
  GC_enable()
```

Приём годится только для коротких и предсказуемых по потреблению памяти
участков — пока GC отключён, ZCT продолжает накапливаться, и это стоит
явно контролировать (например, не выделять внутри такого участка
неограниченное количество новых объектов).

### 3. Soft real-time GC для интерактивных программ

```nim
# компилируется с -d:useRealtimeGC
GC_setMaxPause(500) # жёсткий бюджет паузы: 0.5 мс

proc gameLoop() =
  while true:
    handleInput()
    updatePhysics()
    draw()
    GC_step(500, strongAdvice = false, stackSize = 128 * 1024)
```

Здесь `strongAdvice = false` означает «выполни шаг, только если пороги
`zctThreshold`/`cycleThreshold` уже превышены» — то есть `GC_step`
вызывается каждый кадр, но реальная работа происходит только тогда, когда
она действительно назрела, ограниченная при этом бюджетом в 500
микросекунд.

| Искусственно удержать объект живым (внешний корень) | `GC_ref` / `GC_unref` (`nimGCref`/`nimGCunref`) |
| Выделить новый `ref`/`seq`/`string`                 | `newObj` / `newSeq` (генерируется компилятором) |
| Увеличить `seq`/`string` сверх вместимости           | `growObj`                              |
| Приостановить сборку на время критического участка   | `GC_disable` / `GC_enable`             |
| Принудительно собрать циклические ссылки немедленно   | `GC_fullCollect`                       |
| Отключить только поиск циклов, оставив обычный refcounting | `GC_disableMarkAndSweep`         |
| Посмотреть статистику работы сборщика                | `GC_getStatistics`                     |
| Ограничить длительность одной паузы GC (реал-тайм сборка) | `GC_setMaxPause` + `GC_step`      |

---

## IX. Сводка: что выбрать

- Нужно временно гарантировать отсутствие пауз GC на коротком участке →
  `GC_disable()` / `GC_enable()`.
- Подозреваете утечку на циклических ссылках → `GC_fullCollect()`, затем
  сравните `GC_getStatistics()` до/после.
- Пишете игру или другой интерактивный цикл с жёстким бюджетом кадра →
  соберите рантайм с `-d:useRealtimeGC`, задайте `GC_setMaxPause`, вызывайте
  `GC_step` каждый кадр.
- Хотите оставить обычную очистку памяти, но не тратить время на поиск
  циклов → `GC_disableMarkAndSweep()` / `GC_enableMarkAndSweep()`.
- Нужно понять, что происходит «под капотом» при `a = b`, создании
  `new(T)` или росте `seq` → разделы II–V этого справочника (это внутренние
  механизмы, не публичный API — вызвать их напрямую из пользовательского
  кода нельзя).
